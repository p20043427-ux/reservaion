# 라이브 배포본 분석 (Deployed Build Analysis)

> 대상: https://medical-appointment-nine.vercel.app/#/
> 방법: 라이브 호스트가 본 실행 환경의 네트워크 허용목록에 없어(`Host not in allowlist`) 직접 수신 불가.
> 대신 동일 저장소를 `vite build` 로 빌드하여 **Vercel이 서빙하는 것과 동일한 프로덕션 산출물(`dist/`)** 을 분석함.
> 빌드 도구: Vite 6.4.3 / 분석일: 2026-06-06

---

## 1. 접근 결과 (라이브 직접 수신 시도)

| 방법 | 결과 |
| --- | --- |
| WebFetch | `403 Forbidden` |
| Vercel MCP `web_fetch_vercel_url` | 실패 (이 배포가 연결된 Vercel 계정 소유가 아님) |
| curl (브라우저 UA) | `403 Host not in allowlist` — **실행 환경의 네트워크 정책**이 해당 호스트 차단 |

→ 라이브 응답 바이트 자체는 확보 불가. 단, 배포본은 이 저장소의 빌드 결과이므로 동일 빌드로 재현해 분석함.

## 2. 배포 산출물 (dist/)

```
dist/index.html                 0.48 kB  (gzip 0.34 kB)
dist/assets/index-*.css        11.96 kB  (gzip  2.9 kB)
dist/assets/index-*.js        167.00 kB  (gzip 53.0 kB)
dist/favicon.svg
```

- **단일 JS 청크 + 단일 CSS** (코드 스플리팅 없음 — 앱 규모상 적절).
- 전체 전송량 gzip 기준 약 **56 KB** — 매우 가벼움.
- `index.html` 은 `#root` 빈 div + 모듈 스크립트만 → 순수 클라이언트 렌더 SPA 확인.
- 라우팅은 `vercel.json` 의 `rewrites: /(.*) → /` 로 모든 경로를 SPA로 흡수. 배포 URL의 `#/` 해시는 코드에서 사용 안 함(탭 기반 단일 화면).

## 3. 보안 검증 — 실제 번들 기준 (핵심)

README/아키텍처가 주장한 "브라우저는 절대 OpenRouter 키를 보지 못한다"를 **빌드 산출물에서 직접 검증**:

| 검사 항목 | 클라이언트 번들(dist) 결과 | 판정 |
| --- | --- | --- |
| `sk-or-v1` / `OPENROUTER_API_KEY` 문자열 | **없음** | ✅ 키 미노출 |
| `Bearer ` / `Authorization` 헤더 | **없음** | ✅ 인증 클라이언트에 없음 |
| 모델명 `openrouter/auto` | **없음** (0회) | ✅ 모델 선택은 서버(api/llm.ts) 전용 |
| 호출 엔드포인트 | `/api/llm` **만** (2회) — `openrouter.ai` 직접 호출 없음 | ✅ 프록시 경유 |

→ **보안 설계가 실제 빌드에서 그대로 성립함.** 키와 OpenRouter 직접 호출은 서버리스 함수(`api/llm.ts`, 2.3 KB)에만 존재하고 클라이언트 번들에 전혀 섞여 들어가지 않음 (`vite.config.ts` 의 `loadEnv(...,'')` 가 서버 측에서만 키를 읽기 때문).

## 4. 클라이언트 번들에 노출되는 것 (시크릿 아님, 참고)

`src/lib/openrouter.ts` 가 클라이언트 코드라, 다음은 번들에 그대로 포함되어 **누구나 볼 수 있음**:

- LLM 시스템 프롬프트 2종 — `"병원 접수 데스크의 AI 분류 도우미"`, `"병원 예약 코디네이터 AI"` (각 1회 확인).
- 진료과 목록(`소아청소년과` 3회, `이비인후과` 2회 등), 예시 문의, 검증 규칙.

이는 비밀이 아니므로 문제는 아니나, **프롬프트 인젝션 관점**에서 공격자가 프롬프트 구조를 그대로 알 수 있다는 점은 인지할 가치가 있음(서버 측 프록시에 입력 검증·필터가 없는 현 구조에서는 더 중요).

## 5. 결론

- 배포본은 **순수 정적 SPA(56 KB gzip) + 서버리스 프록시 1개** 구조로, 코드 분석과 100% 일치.
- README가 내세운 **API 키 비노출 설계가 실제 프로덕션 번들에서 검증됨** (키·인증·모델명·외부 직접호출 모두 클라이언트에 없음).
- 잔존 리스크는 코드 분석과 동일: 프록시 인증/레이트리밋 부재, localStorage 단일기기 영속, 의미적 LLM 환각(틀린 진료과/긴급도). 상세는 `docs/ANALYSIS.md` 참고.
- 한계: 라이브 호스트가 네트워크 허용목록 밖이라 **실제 서버 응답·HTTP 헤더·캐시 정책 등 런타임 거동**은 이 방법으로 확인 불가. 필요 시 허용목록 추가 또는 Vercel 계정 연결이 필요함.
